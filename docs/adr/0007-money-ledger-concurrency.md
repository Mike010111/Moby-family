# ADR-007. Деньги: Money, двойная запись, блокировки и идемпотентность

* Статус: принято
* Дата: 2026-11-08

## Решение

* **Money** (`libs/common`) — record над `BigDecimal` со scale 2 (BYN). Конструктор отвергает больше двух знаков,
  `parse` повторяет `parseMoney` прототипа («5,25» допустимо, «1.234» — нет), `format` — «1 200,50 BYN».
  В JPA — `AttributeConverter` → `numeric(19,2)`, в JSON — число. ArchUnit запрещает `double/float` в полях.
* **Ledger двойной записи.** Каждое движение денег — `ledger_transactions` + ≥ 2 `ledger_entries` с нулевой суммой
  (проверяется в `Ledger.post`). Баланс клиентского счёта кэшируется в `accounts.balance`, обновляется только
  в `Ledger` и сверяется с Σ проводок в тестах (`assertLedgerReconciles`: для каждого счёта и Σ по книге = 0).
  Технические счета (эквайринг, клиринг P2P, кэшбэк, входящие остатки) баланс не кэшируют — нет «горячей» строки.
  Выписка ребёнка (`account_operations`) ссылается на проводку; отклонённые оплаты пишутся в выписку без проводки.
* **Проверка и списание — одна транзакция.** `SELECT … FOR UPDATE` по счёту ребёнка (явный native-запрос, затем
  перечитывание сущности; порядок блокировок — по id счёта), после этого — `checkPayment` и лимиты по выписке
  текущего периода, затем проводки. `ConcurrentPaymentsTest`: 50 параллельных оплат — ровно столько успешных,
  сколько позволяет лимит (или баланс), остальные — `LIMIT` (`FUNDS`), ledger сходится.
* **Idempotency-Key** для пополнений, оплат, переводов и операций копилок: запись `(owner_id, key)` с хэшем запроса
  вставляется в той же транзакции, что и операция (`ON CONFLICT DO NOTHING`), ответ сохраняется в `jsonb`.
  Конкурентный повтор ждёт коммита первого запроса на уникальном индексе и получает тот же ответ; тот же ключ с
  другим телом — 409 `IDEMPOTENCY_MISMATCH`. Межсервисные вызовы используют ключи от сущностей (`request:<id>`).

## Альтернативы

* Оптимистичные блокировки (`@Version` + retry) — при всплеске оплат с одной карты дают каскад повторов;
  пессимистическая блокировка строки счёта проще и предсказуемее. `@Version` остаётся как страховка.
* `SERIALIZABLE` — ретраи на всех операциях, без выигрыша для одной горячей строки.
* Event sourcing для ledger — исключён условиями; двойная запись даёт аудит без него.
