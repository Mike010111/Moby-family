# ADR-001. Разбивка на сервисы

* Статус: принято
* Дата: 2026-11-08

## Контекст

Прототип Moby Family — один JS-store в браузере: деньги, семья, награды и уведомления лежат
в одном объекте. Нужен бэкенд, который выглядит как настоящий банковский: деньги хранятся
отдельно и консистентно, остальные функции не могут их повредить и развиваются независимо.

## Решение

Четыре доменных сервиса + gateway, у каждого своя БД (своя база и свой пользователь Postgres):

| Сервис | Граница ответственности | Почему отдельно |
|---|---|---|
| payment | всё, что двигает деньги: счета, ledger, оплаты, P2P, лимиты, категории, заморозка, подписки, автоперевод | строгая консистентность (блокировки, двойная запись, идемпотентность); правила `checkPayment`/`quoteP2P`/лимиты читают одни и те же данные в одной транзакции |
| family | семья и «социальные» сценарии: запросы и одобрения, задания, копилки, уроки, гео | процессы с участием людей и машинами состояний; деньги трогает только через API payment |
| rewards | баллы, магазин артефактов, кэшбэк-предложения | своя экономика (баллы — не деньги), меняется по маркетинговым правилам |
| notification | лента родителя, inbox ребёнка, SSE | чистый консьюмер событий; тексты и доставка отдельно от доменов |
| gateway | единая точка входа, проверка JWT, маршрутизация | фронтенд знает один адрес |

Лимиты и категории — в payment, а не в family: проверка лимита обязана идти в одной транзакции со
списанием под `SELECT … FOR UPDATE` (требование №3). Вынос лимитов в другой сервис означал бы
распределённую транзакцию на каждый платёж.

Копилки — в family (это цель с правилами одобрения), но деньги копилки лежат на SAVINGS-счёте в
payment: денежный инвариант (Σ проводок = баланс) не зависит от family.

## Альтернативы

* **Модульный монолит** (один сервис со Spring Modulith). Проще в эксплуатации и для объёма прототипа
  честно достаточен. Отклонён, так как цель проекта — показать межсервисное взаимодействие
  (outbox, идемпотентные консьюмеры, RestClient с таймаутами). Spring Modulith всё равно используется
  *внутри* каждого сервиса для границ модулей и outbox.
* **Более мелкие сервисы** (limits, subscriptions, piggy отдельно) — больше сетевых вызовов
  в горячем пути оплаты без выигрыша.

## Последствия

* Между сервисами — eventual consistency (события через outbox), кроме мест, где UI ждёт ответа:
  family → payment (переводы при одобрении) и payment → rewards (процент кэшбэка) — синхронно.
* Справочные данные о ребёнке (имя, когорта, семья) частично дублируются в payment/rewards —
  это осознанная денормализация, источник истины — family.
