# Решения по неоднозначностям

Формат: что решено · почему · альтернативы. Архитектурные решения — в `docs/adr/`.

1. **Порт Postgres на хосте — 15432.** Порт 5432 на машине разработки занят; внутри compose
   сервисы ходят на `postgres:5432`. Переопределяется `POSTGRES_PORT`.
2. **Один инстанс Postgres, отдельная БД и пользователь на сервис.** «Своя БД» понимается как
   изоляция данных и прав (сервис физически не может прочитать чужие таблицы), а не отдельный
   процесс: экономит память на стенде. Альтернатива — 4 контейнера Postgres, тривиально меняется в compose.
3. **Коды ошибок сверх JS.** В прототипе часть отказов без кода («Запрос уже обработан», «Не больше 5 копилок»).
   Добавлены коды `VALIDATION, NOT_FOUND, ALREADY_PROCESSED, NOT_NEEDED, TOO_LARGE, PIGGY_MAX, ROOM, UNCHANGED,
   LESSONS_DONE, NOT_FOR_SALE, NOTHING_TO_RENEW, IDEMPOTENCY_KEY, IDEMPOTENCY_MISMATCH, FORBIDDEN, UNAVAILABLE`
   (`libs/common/.../ErrorCode`). Тексты `detail` — дословно из JS.
4. **HTTP-статусы.** Нарушение бизнес-правила — 422; `FROZEN` — 423 Locked (ресурс заблокирован); конфликты
   состояния (`DUPLICATE`, `PENDING`, `SOLDOUT`, `EQUIPPED`, `ALREADY_PROCESSED`, `IDEMPOTENCY_MISMATCH`) — 409;
   ошибки ввода (`AMOUNT`, `COUNT`, `UNIT`, `VALIDATION`) — 400. Статус задан в `ErrorCode`, клиенты опираются на `code`.
5. **Тумблеры → явная установка.** `parent/toggleFreeze` и `parent/toggleAllow` стали `PUT …/frozen {frozen}` и
   `PUT …/categories/{key} {allowed}`: повтор запроса не переворачивает состояние обратно (идемпотентно по смыслу).
   Повторная установка того же значения событий не порождает.
6. **Технические счета без кэшированного баланса.** У SYSTEM-счетов (эквайринг, клиринг P2P, кэшбэк, входящие остатки)
   баланс = Σ проводок, строка не блокируется и не обновляется — иначе все платежи сериализовались бы на одной строке.
   Сверка: для клиентских счетов `balance = Σ entries`, по всей книге `Σ entries = 0` (тест `assertLedgerReconciles`).
7. **Демо-история без проводок.** Исторические строки выписки из initial-state (x1…x5, y1…y8) хранятся как
   информационные; баланс открывается одной проводкой `OPENING` с технического счёта «Входящие остатки».
   Так ledger сходится, а лимиты считают «сегодняшние» траты из истории, как в прототипе.
8. **Какие ответы кэширует идемпотентность.** Сохраняются успешные операции и отклонённые оплаты (отказ записан в
   выписку — повтор должен вернуть тот же отказ, а не создать вторую строку). Отказ, при котором ничего не записано
   (валидация, FUNDS при переводе), откатывает транзакцию вместе с ключом — повтор вычисляется заново и даёт тот же ответ.
9. **Блокировка счёта — явный `SELECT … FOR UPDATE`, затем перечитывание.** `EntityManager.refresh(e, PESSIMISTIC_WRITE)`
   в Hibernate 7 для сущности с коллекцией читает состояние до захвата блокировки; тест на 50 параллельных оплат это
   поймал (ObjectOptimisticLockingFailure). Порядок блокировок — по id счёта.
10. **Кэшбэк — синхронный запрос к rewards до блокировки.** payment спрашивает у rewards процент и баллы
    (`GET /payment-perks`, таймауты 500 мс / 1 с) до транзакции, чтобы не держать блокировку строки во время сетевого
    вызова. Если rewards недоступен — оплата проходит без кэшбэка (метрика `moby.rewards.perks.failures`).
    Деньги кэшбэка зачисляет payment в той же транзакции, что и оплату; событие `CashbackGranted` публикует payment.
11. **Автоперевод.** В прототипе только настройка; в бэкенде — исполнение: проверка каждые 15 минут (ShedLock),
    перевод в день по расписанию (`weekday` 0 = понедельник, как DAYS_ACC), не больше одного в день
    (ключ `autopay:<счёт>:<дата>`). Неуспешный (заморожен, нет денег) в тот же день не повторяется.
    Демо-правила создаются с отметкой «сегодня выполнено», чтобы старт стенда не менял балансы.
12. **Кто что может в payment.** Оплачивать по QR и переводить P2P — только сам ребёнок; пополнять, замораживать,
    менять категории, лимиты и автоперевод — только родитель семьи; подписки — ребёнок или родитель (в прототипе
    их меняет подросток). Чтение счёта — ребёнок (своё) или родитель семьи.
13. **Суммы во входящих запросах — строки** (`"5,25"`): так сохраняется семантика `parseMoney` (запятая, ≤ 2 знаков,
    код `AMOUNT`). В ответах суммы — JSON-числа со scale 2. Внутренние вызовы между сервисами передают числа (`Money`).
14. **Заморозка в family — проекция + payment как последняя линия.** family хранит `members.frozen`, обновляемый
    событиями `AccountFrozen/AccountUnfrozen`, и проверяет его до операций (задания, копилки, запросы) — как в прототипе.
    Пока событие не дошло, денежную операцию всё равно отклонит payment (`FROZEN` пробрасывается как есть).
    Альтернатива — синхронный запрос состояния счёта перед каждой операцией: лишняя задержка и связность.
15. **Копилки не удаляются, а закрываются** (`ACTIVE → COMPLETED | CLOSED`): история и ссылки запросов остаются
    целыми; в API отдаются только активные. Деньги копилки — SAVINGS-счёт payment, `saved` — зеркало из ответа payment.
16. **Порядок проверок при пополнении копилки.** В прототипе «не хватает денег» проверяется раньше «до цели осталось».
    В бэкенде family проверяет остаток до цели сам, а нехватку денег — payment (family не знает баланс). Отличие
    видно, только если нарушены оба условия сразу; ответ в этом случае — `ROOM` вместо `FUNDS`.
17. **Получатель P2P для запроса сверх лимита.** Справочник контактов живёт в payment; `GET /p2p/quote?contactId=`
    возвращает имя контакта, family не дублирует справочник.
18. **Отмена запроса при одобрении.** Если копилки уже нет, запрос переходит в `CANCELLED` и это сохраняется, а клиент
    получает 404 (`@Transactional(noRollbackFor = RequestCancelledException.class)`), как в прототипе.
19. **Баллы за действия в family** (урок +10, задание +5, копилка +2) задаёт family и передаёт в событии (`points`):
    это правила вовлечения в семейные сценарии. rewards хранит баланс баллов и правила магазина; баллы за покупку
    (`max(1, round(amount))`) — правило rewards.
20. **Спецификация на Node 25.** В Node 25 появился глобальный `sessionStorage`, и прежний Store стал переносить
    состояние между тестами (`fresh()`), из-за чего 8 сценариев падали ещё в исходном прототипе. `npm test`
    запускается с `--no-experimental-webstorage` — все 25 сценариев зелёные; код спецификации не менялся.
21. **Генератор случайных чисел для GPS-демо** — `java.util.Random`: в Alpine-JRE нет модуля `jdk.random`,
    и `RandomGenerator.getDefault()` падает при старте.
22. **Образы.** Один multi-stage Dockerfile: стадия сборки одинакова для всех сервисов (собирает все jar-ы один
    раз, кэш Gradle — BuildKit cache mount), runtime — `eclipse-temurin:21-jre-alpine`, непривилегированный
    пользователь, healthcheck по `/actuator/health/readiness`. Лимит памяти 512 МБ, SerialGC — стенд должен
    помещаться на ноутбуке рядом с Keycloak и Kafka.
23. **Фронтенд за nginx на :5173**, `/api` проксируется на gateway (один origin, без CORS для API); Keycloak — на
    :8180 напрямую (CORS через `webOrigins` клиента). SSE-локация без буферизации, таймаут чтения 1 ч.
